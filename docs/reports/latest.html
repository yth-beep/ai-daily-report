【嵌入式Linux入门教程 19】RK3506 开发环境搭建与交叉编译｜从 sysroot、工具链配置到 Hello World 上板运行

bilibili · WwuSama · 嵌入式 Linux 基础（当前主线）

视频链接：https://www.bilibili.com/video/BV1HFsE6pERR

推荐等级：强烈推荐

核心问题：板子能跑 Hello World 之前，主机侧那套交叉编译环境到底由哪几块组成、库和头文件从哪来，即 sysroot 是什么、怎么接进工具链。

关键方法 / 结论：思路是先拿 sysroot 再配工具链：Buildroot 编译 SDK 时除了产出烧到板上的 rootfs，还会在 output 下产出一份 host 侧 sysroot（arm-buildroot-linux-gnu 目录），里面的 /usr 下就是板子实际带的头文件与 .so/.a 库，Qt、cURL 等已默认编进去。因为该路径很长、且重新编译 Buildroot 后内容会变，视频不直接拷贝而是用软链接指过去，这样库更新后无需重新搬一遍。后面再讲工具链如何指向这个 sysroot、以及编出 Hello World 上板运行。

为什么推荐：交叉编译是从“会敲 Linux 命令”跨到“能给开发板做东西”的第一道门槛，而 sysroot 正是最容易卡住的地方——库找不到、头文件版本不匹配、链接时报 undefined reference，多数根因都在这里。这条把 sysroot 的来源和软链接做法讲清楚了，正好接在你当前的嵌入式 Linux 主线上。

适用场景：拿到开发板、SDK 已编译完成、准备第一次写自己的程序上板时看最合适；也可当作后面往 rootfs 里加第三方库（MQTT、TFLite 之类）的前置知识。

Linux 运维实战 EP05：systemd 服务起不来，别急着 restart，先留现场

bilibili · Vicky_DW · 嵌入式 Linux 基础（当前主线）

视频链接：https://www.bilibili.com/video/BV1uHu66XEE3

推荐等级：推荐

核心问题：systemd 服务启动失败时，为什么不该连着 restart，以及按什么顺序把“现场”留住再去重启验证。

关键方法 / 结论：核心是先取证再动手：连续 restart 会让每次失败的时间线互相叠加，原始退出码和第一次失败的现场反而被噪声盖住。要留的是三样——主进程退出码、失败发生的时间点、以及失败前最后几行日志；日志窗口要缩到故障前后十几分钟，只看最后一行常会漏掉更早的配置错误、权限问题或资源不足。再确认 systemd 实际加载的是哪份 unit 和 drop-in 覆盖配置（刚改的文件不一定就是生效的那份），若日志指向端口占用或依赖服务，就顺着那个对象继续查。最后才重启，让重启成为有依据的验证而不是碰运气。

为什么推荐：这条给的不是某个命令，而是一套排障顺序，属于能反复复用的方法论。嵌入式设备上服务起不来极常见，且板子往往没法随时重刷，学会先留现场能省下大量瞎试时间；它和你正在看的 journalctl、systemd 内容正好串成一条线。

适用场景：第一次给开发板写自启服务、或调试开机后某个守护进程没起来时直接用；也适合作为日常运维排障的检查清单。

应付公司检查，清理穿帮日志，十多年的Linux老用户被迫学习journalctl

bilibili · 飞蚊话 · 嵌入式 Linux 基础（当前主线）

视频链接：https://www.bilibili.com/video/BV17Lsp6ZEaW

推荐等级：推荐

核心问题：journalctl 到底是不是“记日志的程序”，日志究竟由谁写入、来源有哪些、又该怎么限制它占用的空间和保留时间。

关键方法 / 结论：关键区分是分工：真正接收并保存日志的是 systemd-journald 服务，journalctl 只是读取和查询已存日志的前端，所以它本身不产生日志。日志来源比想象的多——内核通过 kmsg 机制进来的硬件初始化与驱动加载消息（-k 看到的就是这批）、各 systemd 服务的标准输出与标准错误、syslog 接口的传统来源，以及 audit 子系统的审计记录，因此不带参数直接跑才会又全又乱。相较 /var/log 下每个程序各写各的 .log 文本，journal 是集中且带结构化字段的。视频后半段接着讲只保留一定时间该怎么设置，这部分留作动手时再看。

为什么推荐：把“谁写、谁读、从哪来”理清之后，前面的 -k、-u、-b 这些参数就不再是死记，而是能推出来该往哪查。嵌入式场景里日志默认多在内存、重启即丢，理解 journald 的存储与保留策略直接关系到板子 Flash 空间和掉电后还能不能查到故障。

适用场景：在已经会用 journalctl 基本参数之后看，用来补底层模型；等要配置日志持久化、限制 journal 体积或排查掉电后日志丢失时，再回来看保留时间的设置部分。
