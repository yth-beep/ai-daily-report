【实验记录 EP10】280 条崩了 300 条又好，为什么｜DeepSeek 小满

bilibili · 打工的小满 · AI 大模型

视频链接：https://www.bilibili.com/video/BV1Tzs166EfZ

推荐等级：强烈推荐

核心问题：同一个长文档任务“280 条崩了、300 条又好”，抖动到底是上下文长度的硬阈值、量化精度不够，还是别的东西在起作用。

关键方法 / 结论：作者用了一套很干净的控制变量法。先把上下文窗口锁死在 2 万 4 只改文档长度：1.1 万字 30 轮全对；1.3 万字第一轮就崩；只再多加 20 条，又全对了；1.5 万字再崩。为排除运气，同一长度连跑三次，三次结果一模一样，说明这个位置确实“站不稳”。再把同一位置换成 16 位精度，崩照旧，量化的嫌疑也洗清。最后把其中一条要求拿掉——那句“先报口令编号”——不加强制口令时全对。结论不是某条长度阈值，而是模型同时要维持几件事（口令、长文档、输出格式）时被挤爆，作者的原话是“不是阈值，是他同时要记几样东西”。

为什么推荐：它把“长上下文能力”从厂商标称的支持多少 token，拽回到“同一时刻要并行维持几条约束”的工程问题上，这正好是写 prompt、做长文档抽取时最容易被忽略的变量。更值钱的是方法本身：锁定单一变量、连跑三次验可复现、再逐条剥离干扰项——这套动作可以直接搬进你自己的任何模型实验，比再多看十篇评测都有用。

适用场景：做 RAG、长文档抽取、或多约束指令任务（同时要求格式、编号、内容口径）之前看。也适合用来给自己解释一个常见困惑：为什么上下文明明没超窗口，答案还是掉；以及为什么“加一条格式要求”会让整体正确率断崖。

ROS 2机器人×LLM 智能体: 本地模型部署, MCP协议与安全实践

bilibili · Theitzy资源网 · AI 大模型

视频链接：https://www.bilibili.com/video/BV1uis16kEx1

推荐等级：推荐

核心问题：让一个本地小模型去控制机器人，成功率的瓶颈究竟在模型不够聪明，还是在“你给了它什么工具”。

关键方法 / 结论：实验设计得很干脆：普通笔记本、纯 CPU 就能跑，Qwen2.5-3B 由 Ollama 本地服务（下载约 1.9GB，不用注册、不用 API key、不走云），任务是让仿真乌龟到达 20 个目标点，只改变工具集。只给基础速度工具，20 个目标到达 0 个；加一个转向工具，到达 15 个；只保留任务真正需要的那几个工具，20 个全中。评分标准是关键设计：只看机器人实际到达的位置，从不采信模型自己声称“我到了”。配套还给了 fixed 与 broken 两套代码和一条命令的 verify.sh，要求报错必须打印真正的失败行而不是崩溃，让人先确认环境和检查脚本本身是对的，再让模型介入。

为什么推荐：0 → 15 → 20 这组数字把“智能体效果差”从玄学变成了可调参数：工具粒度就是那个旋钮。它同时示范了两个工程习惯——用外部可观测结果当评分依据（不信模型自述），以及先把环境校验跑通再上模型，这两点在你自己搭智能体（尤其是接硬件/执行器）时会反复救你。另外它还证明了一件事：3B 级本地模型配好工具，能做的不比云端大模型差太多。

适用场景：准备让大模型去驱动任何真实执行器（小车、机械臂、仿真环境）之前必看，可以直接抄它的工具粒度消融实验；也适合当作本地小模型 + MCP 的最小可行範例，先在笔记本上把 agent 闭环跑通，再考虑搬到板子上。

重要内容

ESP32开发之ESP-IDF也玩设备树

bilibili · 命叔杂技 · 嵌入式 Linux

视频链接：https://www.bilibili.com/video/BV1t1sB6pEaW

推荐等级：推荐

核心问题：一套固件要同时适配多块开发板，硬件差异只能靠一堆编译条件分支堆在驱动里，越加越容易出错——怎么把“板级差异”从代码里赶出去。

关键方法 / 结论：作者给原生 ESP-IDF 加了一层轻量设备树（LWDT，Apache-2.0 开源）。做法是用一份分层 JSON 描述处理器、开发板和板上外设，构建时读取板级配置、由该 JSON 生成 C 宏，硬件参数在编译期就确定下来，运行时不需要解析，零额外开销。驱动则按启动优先级分层初始化：时钟、GPIO、总线、再到应用层，顺序固定。效果是换开发板只改一个板子编号，驱动代码不用跟着板卡改动，同时保留 ESP-IDF 原生驱动与 CMake 构建生态，属于“轻量接入”而不是另起一套框架。

为什么推荐：设备树是 Linux 里“硬件描述与驱动解耦”的标准答案，这条把它搬到了 MCU 侧，等于用你嵌入式 Linux 主线里正在学的概念去解释 ESP-IDF 的工程组织方式，两边能对上号。而且“一份描述复用多块开发板”是从单板点灯走向产品化的必经一步，早一点建立这个分层意识，后面看内核设备树、看 BSP 分层都不会陌生。

适用场景：手上有两块以上开发板、或同一份工程要交付给不同硬件版本时直接可用；现在也可以当作“设备树到底解决什么问题”的低门槛样本，先把 JSON 描述硬件 → 编译期生成配置这条链路看明白，再回去读 Linux dts 会顺很多。
