嵌入式 Linux

重要内容

嵌入式Linux刚改完配置就拔电源，为何变0字节甚至只读变砖？看懂Page Cache延迟落盘、四步原子写与SquashFS抗掉电

bilibili · RobinLi609 · 嵌入式 Linux

视频链接：https://www.bilibili.com/video/BV1qH1pzxE18

推荐等级：强烈推荐

核心问题：现场随手拔电源时，为什么写入接口明明返回成功，配置文件还是会变成 0 字节、根文件系统甚至直接只读变砖？抗掉电到底该在哪几层设防？

关键方法 / 结论：先拆两个根因。第一，write/close 返回成功只说明数据进了内核 page cache 的脏页，回写线程默认十几到三十秒才异步刷盘，掉电时内存里的新内容直接蒸发。第二，习惯用截断标志（O_TRUNC）原地打开配置文件，会先把旧文件的数据块清零，而新配置还躺在断电就消失的内存脏页里，于是重启后拿到一个文件名还在、内容为 0 的空壳。关键配置要严格走四步原子落盘：① 先把完整新配置写进同目录的临时文件，绝不动原文件；② 关闭前显式调用 fsync（字幕转写成「强制同步死」），等闪存控制器把数据块真正写入物理介质再返回；③ 同分区 rename 原子替换文件名指针；④ 打开父目录再 fsync 一次，把新的目录项也落盘。同时划寿命红线：秒级高频日志严禁每次 fsync，写入放大会很快把工业闪存刷出坏块，应走内存缓冲加异步批量写。整机层做第二、第三道防线：把 rootfs 打成只读压缩分区（SquashFS），现场永不写入，掉电一万次也照样秒开；再用叠加文件系统挂一个独立数据分区专存用户配置，极端损坏也能一键重置。

为什么推荐：这是纯嵌入式 Linux 的系统可靠性问题，串起 page cache 延迟回写、文件系统原子性、只读根加 overlay 隔离三层，属于产品化落地时最容易翻车、也最难在课堂上讲透的部分。它讨论的是掉电一致性与存储介质寿命，不是模型能力或推理性能，因此归嵌入式 Linux，不要和 AI 侧内容混看。

适用场景：做网关、工控屏、门禁、自助终端这类会被现场直接拔电的产品，进入出厂随机断电测试或现场故障复盘阶段时用；也适合当文件系统章节的实例，用来理解「写入返回成功」与「数据真正持久」之间的语义差。
