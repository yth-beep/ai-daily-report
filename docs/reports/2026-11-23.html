推荐等级：强烈推荐

核心问题：循环语言模型每个 token 都要跑完全部循环，延迟随循环深度线性上涨；早停能省算力却会让上下文停在不成熟的浅层状态，有没有办法既快又不掉准确率？

关键方法 / 结论：论文反着做，叫「晚进入」：跳过最初几次循环，把新 token 的原始 embedding 直接送进最后 K 次循环，并复用这些循环已经算满全部梯次的深度 KV 缓存。直接注入会崩，原因是表征分布不匹配——浅层循环吃的是原始 token embedding（L2 范数中位数约 0.76），深层循环吃的是前面循环输出的层归一化隐状态（范数 37~51）；只需少量微调让深层循环适配原始输入，效果反而超过早停。实验还给出一个不对称结论：同样 K 次串行计算，放在循环末尾比放在开头更好，T=4 时「一次末尾循环 + 四次深度上下文」比「两次初始循环 + 两次浅上下文」准确率高十个百分点以上，说明深度缓存本身已保留了大部分循环深度带来的收益。落地靠「晚进入快解码 + 投机验证」：把非关键路径与关键路径解耦，临时接受的 token 借每次推理调用的空闲 batch 容量补算全量循环，不增加额外串行调用。

为什么推荐：属 AI 大模型侧的推理加速前沿：它同时给出机制解释（KV 缓存该缓到哪一层，决定了上下文是否成熟）和可迁移的工程套路（改微调目标对齐分布 + 借 batch 冗余做投机验证）。对理解早停、投机解码、循环/共享层模型这几条路线的关系很有帮助，比只看「加速几倍」的标题有用得多。

适用场景：适合在已熟悉 Transformer 解码与 KV 缓存、开始比较推理加速方案（早停、投机解码、循环深度共享）时读；做服务端或端侧延迟优化选型时可作为一条独立对照路线。

核心问题：小模型做垂直领域语义解析（语音点单这类），输出格式该选紧凑符号还是自然语言？「输出越短越准」这个直觉成立吗？

关键方法 / 结论：作者先做咖啡厅点单解析器时选了紧凑格式提速，手写小测试集根本测不出格式差异，换到公开 pizza 数据集才看清。研究把「输出长度」与「表层形式」两个变量拆开：为目标语义设计六种无损编码，并做两组长度匹配对照，跨两个模型家族、五种训练池规模、五个随机种子验证。结论是长度本身不是机制——只有当表层形式仍是自然语言单词时缩短才有效，换成符号后短反而更差，自然语言编码 token 更多却更准。指标上把静默错误率 S（能解析成合法结构但语义错，用户拿到餐才发现）单独拎出来当部署指标，与精确匹配率 A 并列报告；并给每个模型加护栏处理菜单外输入与口语自我修正，同时量化护栏的收益与成本。

为什么推荐：属 AI 大模型侧的部署可靠性话题：它把「上线后最怕的不是报错而是静默出错」量化成可对齐的指标，并给出一套能直接照搬的实验设计（长度匹配的对照组、多随机种子、按错误类型分桶）。对小模型落地比追榜单更有用，也顺手教了怎么读一篇「反直觉结论」的论文。

bilibili · WwuSama · 嵌入式 Linux

视频链接：https://www.bilibili.com/video/BV1hty5zxEU8

推荐等级：强烈推荐

核心问题：板子上缺一个第三方库时，是回到 SDK 的 Buildroot 里重新配置整个根文件系统，还是拿现成的交叉编译工具链单独编一个库塞进项目？两者分别该在什么阶段用？

关键方法 / 结论：两条路线的取舍讲得很直接。走 SDK 内置 Buildroot：重新勾选需要的库并整编 rootfs 再烧录，优点是依赖与版本由构建系统统一管理、产出的固件可直接量产批量烧录，缺点是库版本被 Buildroot 钉住，想换新版得改配置、处理新版本带来的依赖变化，最后仍要重编整个根文件系统。手工路线：下载第三方源码，用现成的 sysroot 加交叉编译工具链单独编译，版本与编译选项自由、可单独部署到板子，适合前期调试，但传递依赖要自己一个个补（这个库依赖别的库就得把底层库一起编好），版本管理与批量部署都更麻烦。前提也点明了：板子用的 Buildroot 这类构建系统没有 apt 那种包管理器，构建时没配进去的库只能自己补。实战部分以「给项目加一个带日志等级与固定格式的日志库」为场景，串起编译、链接集成到上板运行。

为什么推荐：属嵌入式 Linux 侧的构建系统基本功：交叉编译第三方库是每次给板子加功能（HTTP、JSON、日志）都会撞上的第一道坎。这条把 Buildroot 重编与手工交叉编译的适用边界摆清楚，也解释了为什么板端没有包管理器、为什么「加一个库」有时意味着重烧一次固件，属于看一遍就能少绕弯的内容。

适用场景：适合在已拿到 RK3506 这类 SDK、开始把开源库集成进业务程序的上板阶段看；也可在决定「要不要为了一个库整编固件」时用来对照两条路线的代价。
